# Changelog — Python Embed Installer (get_con.cmd / get_win.cmd)

## [26.0807] — 2026-08-07

### get_con.cmd + новый bootstrap.ps1 — удалённый запуск через `irm | iex`

**Добавлено:**
- Новый файл `bootstrap.ps1` — отдельный загрузчик для запуска установки одной командой без
  скачивания `get_con.cmd` на диск вручную:
  ```powershell
  irm https://raw.githubusercontent.com/<user>/<repo>/main/bootstrap.ps1 | iex
  ```

**Изменено — get_con.cmd:**
- `$ScriptDir` теперь имеет значение по умолчанию `$PWD.Path` (текущая директория) вместо
  отсутствия значения. При обычном локальном запуске это ничего не меняет — batch-обёртка
  всегда явно передаёт `-ScriptDir "%SCRIPTDIR%"` (директорию самого файла). Но при удалённом
  запуске через `bootstrap.ps1` файла на диске не существует, поэтому нужен разумный дефолт —
  им стала директория, из которой вызвана команда. В этом сценарии `pyconfig.json` /
  `requirements.txt` подхватываются оттуда же, и туда же распаковывается `python/`.

**Версия:** `26.0801` → `26.0807`.

## [26.0801] — 2026-08-01

### get_con.cmd — ключ `-NoWait` для безголового вызова из другого `.cmd`

**Добавлено:**
- Параметр `-NoWait` (PowerShell `[switch]`) — подавляет финальный
  `Read-Host -Prompt "Press any key to continue"` после блока `COMPLETE`.
- На уровне batch-обёртки: если среди аргументов `%*` встречается `-nowait`
  (без учёта регистра), итоговый `pause` при ненулевом коде возврата (`RC`) тоже
  пропускается — сценарий, где `get_con.cmd` вызывается через `call` из другого
  скрипта (например, `make.cmd`) и не должен зависать на ожидании клавиши ни при
  успехе, ни при ошибке.

**Не изменено:**
- Без ключа поведение прежнее — оба ожидания клавиши (`COMPLETE` и `pause` при
  ошибке) остаются, как для обычного интерактивного запуска.
- Ключ никак не влияет на приоритет `-PyVer`/`-Arch` → `pyconfig.json` →
  интерактив — это независимый флаг, добавляется к остальным ключам:
  ```bat
  get_con.cmd -PyVer 3.14.1 -Arch amd64 -NoWait
  ```

**Версия:** `26.0731` → `26.0801`.

## [26.0731] — 2026-07-31

### get_con.cmd — ключи командной строки для выбора версии/архитектуры

**Добавлено:**
- Именованные параметры `-PyVer` / `-Arch` для запуска без единого диалога, удобно для вызова
  из другого `.cmd`-скрипта:
  ```bat
  get_con.cmd -PyVer 3.14.1 -Arch amd64
  ```
- Функция `Read-CliConfig` — читает и валидирует значения из `-PyVer`/`-Arch`.
  - Ни один ключ не задан → `$null`, ничего не меняется.
  - Задан только один из двух → явная ошибка («оба ключа обязательны вместе»).
  - Формат версии/архитектуры некорректен → та же ошибка, что и для `pyconfig.json`.
- Проверка формата вынесена в общую функцию `Test-PyConfigValues` — используется и
  `Read-PyConfig`, и `Read-CliConfig`, без дублирования правил валидации.

**Приоритет источников:** ключи командной строки → `pyconfig.json` → интерактивный выбор.
Если заданы оба сразу (и ключи, и файл) — используются ключи, о чём выводится отдельное
сообщение; `pyconfig.json` в этом случае молча не трогается.

**Сценарий «версия не найдена на python.org»** (`[S]elect version manually` / `[C]ancel`,
с записью выбора обратно в `pyconfig.json` при ручном выборе) — работает одинаково независимо
от того, откуда пришёл исходный запрос: из ключей или из `pyconfig.json`.

**Выбор формата ключей:** сначала был реализован вариант `-pyver=3.14.1 -arc=amd64`
(через ручной парсинг одной строки регулярками), но по итогам обсуждения заменён на
нативный именованный параметр PowerShell (`-PyVer 3.14.1`, пробел вместо `=`). Причина —
PowerShell разбирает такие параметры «из коробки», без необходимости писать свой парсер
аргументов; батник теперь просто прокидывает `%*` напрямую, без обёртки в одну строку.
Альтернативный классический batch-стиль (`/PyVer:3.14.1`) не рассматривался как финальный
вариант — PowerShell не умеет парсить `/`-параметры, так что выигрыша в простоте он не дал бы.

**Версия:** `26.0730` → `26.0731`.

### get_con.cmd — поддержка `requirements.txt` для установки пакетов

**Добавлено:**
- Функция `Read-Requirements` — читает `requirements.txt` рядом со скриптом (пропускает
  пустые строки и строки, начинающиеся с `#`), портирована без изменений из `get_win.cmd`.
- Функция `Install-Requirements` — ставит пакеты из файла через `pip install -r`, с логированием
  в консольном стиле (`Write-Status`/`Write-OK`/`Write-Fail`), в отличие от `Install-Packages`,
  которая ставит фиксированный список напрямую.

**Изменено:**
- `$PACKAGES` переименована в `$DEFAULT_PACKAGES` — для консистентности с `get_win.cmd`, раз
  теперь это именно значение по умолчанию, а не единственный вариант.
- Логика выбора: если `requirements.txt` найден и непуст → ставится он (`Install-Requirements`);
  иначе → `$DEFAULT_PACKAGES` (`pyinstaller`, `fonttools`) через `Install-Packages`, как и раньше.
- Стартовый баннер и итоговый блок `COMPLETE` обновлены, чтобы показывать, откуда взят список
  пакетов (`requirements.txt` с числом строк, либо явный список по умолчанию).

Консольная и GUI-версии теперь читают `requirements.txt` независимо друг от друга (разные
экземпляры файла в разных папках, если версии лежат отдельно) и обрабатывают его одинаково.

**Версия:** без дополнительного бампа — входит в `26.0731`.

### get_win.cmd (GUI-версия)

**Изменено — поведение по умолчанию без `requirements.txt`:**
- Раньше при отсутствии `requirements.txt` устанавливался только pip («pip only»).
- Теперь по умолчанию ставятся `pyinstaller` и `fonttools` (последние версии) — приведено в
  соответствие с консольной версией.

**Добавлено:**
- `$DEFAULT_PACKAGES = @("pyinstaller", "fonttools")` — константа списка пакетов по умолчанию.
- Функция `Install-Packages` — устанавливает список пакетов напрямую через
  `pip install <pkg> <pkg> ...` (в отличие от `Install-Requirements`, которая ставит из файла
  через `pip install -r`).

**Логика:**
- Если `requirements.txt` найден и непуст → как и раньше, ставится он (`Install-Requirements`).
- Если файла нет → ставится `$DEFAULT_PACKAGES` (`Install-Packages`).

**Обновлены статусные сообщения и итоговый отчёт**, чтобы отражать, что именно
устанавливается в режиме по умолчанию.

**Версия:** `26.0711` → `26.0730`.

### get_con.cmd (консольная версия)

**Добавлено — выбор версии/архитектуры Python через конфиг-файл:**
- Функция `Read-PyConfig` — читает и валидирует `pyconfig.json` (лежит рядом со скриптом,
  в `$ScriptDir`).
  - Файла нет → возвращает `$null`, ничего не меняется (интерактивный выбор как раньше).
  - Файл есть, но:
    - невалидный JSON,
    - отсутствует `version` или `arch`,
    - `version` не в формате `3.12.4` (regex `^\d+\.\d+\.\d+$`),
    - `arch` не `amd64`/`win32`

    → скрипт завершается с явной ошибкой (`Write-Fail` + `exit 1`), без тихого отката на
    интерактивный режим.
- Конфиг читается сразу после проверки соединения, **до** запроса списка версий с python.org —
  ошибка в файле ловится мгновенно, без лишнего сетевого запроса.
- Если версия/архитектура из конфига валидны по формату, но такой сборки **нет** на
  python.org — явная ошибка с подсказкой:
  - какие архитектуры реально доступны для запрошенной версии, либо
  - что версии вообще не существует.
- Если `pyconfig.json` отсутствует — поведение не изменилось: `Select-FromList` для версии,
  затем для архитектуры (если доступно больше одной).

**Формат `pyconfig.json`:**
```json
{
    "version": "3.12.4",
    "arch": "amd64"
}
```

**Изменено — поведение при отсутствии запрошенной версии на python.org:**
- Раньше: версия/архитектура из `pyconfig.json` не найдена на python.org → скрипт сразу
  завершал работу (`exit 1`) после вывода ошибки.
- Теперь: после сообщения об ошибке (с подсказкой по доступным архитектурам либо о том, что
  версии нет вообще) скрипт предлагает выбор:
  ```
  [S]elect version manually / [C]ancel
  ```
  - `C` — завершить выполнение (прежнее поведение).
  - `S` — перейти в интерактивный режим выбора версии/архитектуры, как если бы
    `pyconfig.json` не было вовсе.
  - Некорректный ввод — повторный запрос.
- Интерактивный выбор вынесен в отдельную функцию `Select-BuildInteractive`, чтобы не дублировать
  код между обычным сценарием (без конфига) и этим фолбэком.

**Добавлено — запись выбора обратно в `pyconfig.json`:**
- Функция `Write-PyConfig` — перезаписывает `pyconfig.json` парой `version`/`arch` в том же
  формате, что читает `Read-PyConfig`.
- Срабатывает **только** в сценарии `[S]elect version manually` (когда версия/архитектура из
  `pyconfig.json` не найдена на python.org, и пользователь выбрал её вручную) — выбор
  перезаписывается в файл, служит маркером того, что реально было установлено.
- Если `pyconfig.json` изначально отсутствовал (обычный интерактивный запуск без конфига вовсе) —
  файл **не создаётся**. Записывается только при исправлении уже существующего, но
  невалидного/устаревшего конфига.

**Версия:** `26.0711` → `26.0730`.

### Осознанное решение — не переносить в get_win.cmd

`pyconfig.json` в GUI-версию **намеренно не портирован**. GUI-версия ориентирована на
неподготовленного пользователя (выбор из списка мышкой), а не на того, кто готов вручную
писать конфиг-файл — такому пользователю нужна консольная версия. Расхождение задокументировано
здесь, чтобы не путать с недоделкой при следующих правках.

---

### Известные проблемы (не исправлено в этом релизе)

- **get_con.cmd**, функция `Invoke-Python`: `$script:_lastErr` всегда устанавливается в пустую
  строку (`Start-Process` без перехвата stdout/stderr), в отличие от `get_win.cmd`, где
  `Invoke-Python` честно перехватывает вывод процесса. Из-за этого сообщения об ошибках pip/python
  в консольной версии не содержат деталей (`... failed: ` без текста ошибки).
  Отложено по просьбе пользователя — требует переноса логики перехвата stdout/stderr из
  GUI-версии в консольную.
